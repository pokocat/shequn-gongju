# 员工与服务资源页面审查

日期：2026-09-15  
审查范围：`?view=pc&module=cs` 的员工台账、服务官配置、客服与服务团队、角色与权限。  
审查目标：让“员工、服务关系、权限”成为一条清晰的管理链路，减少重复页面和重复按钮。

## 当前结论

“员工与服务资源”作为统一入口是正确方向，但当前四个页签仍然像四个并列页面，缺少一个共同的员工档案中心：

`员工档案 -> 岗位与权限 -> 服务官资格 -> 服务范围 -> 账号/群资源`

最需要收敛的地方是“员工台账”和“客服与服务团队”。前者已经显示岗位、服务范围、主服务官、账号资产；后者只是同一个表格的筛选结果，字段和操作几乎重复。因此它不应继续作为独立主页签。

## 优点

1. 侧边栏已合并为“员工与服务资源”，避免“客服”与“员工权限”分散。
2. 员工台账能同时展示原客服人员与系统员工，统一方向正确。
3. 服务官配置已经明确展示项目、地区、在用账号和备份服务官，关键关系开始可见。
4. 新建员工入口比“新建客服”更符合统一员工模块。
5. 角色与权限复用了既有权限矩阵，可继续保留作为基础能力。

## 主要问题

### P0：员工台账和客服与服务团队重复

现状：两个页签都是员工列表，搜索、状态筛选、分页、查看、停用、归档完全相同。

影响：用户不清楚什么时候进入“客服与服务团队”；维护两套页面也容易造成字段、状态和操作不一致。

建议：取消“客服与服务团队”主页签，改为员工台账中的保存视图/快速筛选：

- 全部员工
- 服务团队
- 服务官
- 待配置
- 已停用

服务团队视图仅展示服务相关列：服务项目、服务地区、主服务官、备份服务官、排班状态、负责群数、服务容量。

### P0：服务官定义与资格来源不够严格

现状：服务官由“客服、项目负责人、区域运营”三类身份推导，容易让项目负责人或区域运营自动成为服务官。

影响：服务官是具体服务责任人，不应由岗位名称隐式推断；会导致无实际服务排班的人进入匹配列表。

建议：增加独立的“服务官资格”开关，仅已启用员工可勾选。资格卡包含：

- 是否可担任主服务官
- 可服务项目
- 可服务地区
- 最大客服人数 / 最大群数
- 备份服务官
- 当前负载和状态

项目负责人、区域运营可以具备服务官资格，但必须显式启用。

### P1：服务官配置使用技术 ID，而不是业务名称

现状：卡片显示 `p_beijing_pro`、`p_shanghai_exp`。

影响：运营人员无法快速识别项目；技术 ID 只适合后台开发或悬停信息。

建议：默认展示“北京 PRO 会员”“上海体验官”等业务名，技术 ID 放到悬停提示或编辑弹窗内。

### P1：服务范围缺少结构化关系

现状：项目、地区、备份服务官可配置，但服务范围是自由文本，且没有主服务官和服务团队的双向校验。

影响：同一项目/地区可能出现多个主负责人；客服可被分给不具备服务资格的人。

建议：服务范围改为结构化记录：

| 字段 | 规则 |
|---|---|
| 服务项目 | 必选，可多选 |
| 服务地区 | 可多选；未设置则表示项目全域 |
| 主服务官 | 每个“项目 + 地区”唯一 |
| 备份服务官 | 可选，不能等于主服务官 |
| 服务团队 | 可多选客服 / 服务老师 |
| 容量上限 | 客服人数、群数、会员数 |

### P1：角色与权限页是嵌入式的第二个页面

现状：切换到“角色与权限”后出现一套独立页面标题、独立左栏、独立审计栏，和外层“员工与服务资源”的标题与页签形成双层页面结构。

影响：层级重复，内容区域拥挤；用户不知道“角色”和“员工”如何关联。

建议：将权限页改为员工详情内的“权限”子页，外层保留“权限模板”作为次级入口。新结构：

- 员工台账：员工列表
- 服务关系：服务官覆盖、客服团队、排班与容量
- 权限模板：角色模板和权限矩阵

点击员工后，在右侧详情/抽屉里配置：基础资料、服务关系、账号资源、权限、操作日志。

### P1：主操作过多且缺少阶段区分

现状：员工行同时出现查看、停用、归档；服务官卡还有单独的配置按钮。

建议：行内只保留“查看”；停用、归档、变更服务官、分配资源收进员工详情的更多操作。归档只在无账号、无群、无审批时可用。

### P2：当前数据语义不一致

现状：原客服数据的岗位仍是“探哥 / 假面”，服务范围统一显示“AI学习社群”，与新模块的项目、服务官概念不一致。

建议：数据迁移时做一层映射：

- 探哥 / 假面 -> 历史服务标签，不再作为岗位
- 岗位改为客服专员 / 服务老师 / 社群运营 / 项目运营 / 项目负责人
- 服务项目和地区来自服务关系配置，不从历史昵称推导

## 推荐信息架构

建议将四个页签收敛为三个：

1. **员工台账**：全部员工，一处入口管理建档、状态、账号资源和查看详情。
2. **服务关系**：包含“服务官覆盖”和“服务团队”两个分段，管理项目/地区到服务官和客服团队的关系。
3. **权限模板**：管理角色模板、数据范围、模块权限；员工实际权限在员工详情内引用模板并支持少量例外。

员工详情建议统一为五个子页：

| 子页 | 内容 | 主按钮 |
|---|---|---|
| 档案 | 基础资料、部门、岗位、状态 | 编辑档案 |
| 服务关系 | 项目、地区、主/备服务官、负责群、容量 | 保存服务关系 |
| 账号资源 | 分配的微信、企微、手机号、系统账号 | 分配资源 |
| 权限 | 角色模板、数据范围、例外权限 | 调整权限 |
| 记录 | 变更、交接、停用、归档、审批 | 查看审批 |

## 推荐操作规则

| 场景 | 系统动作 |
|---|---|
| 新建普通员工 | 创建档案，状态为启用或待激活；不自动成为服务官 |
| 新建客服 | 创建档案后选择服务项目和地区；系统只匹配已启用且具有服务官资格的人员 |
| 配置服务官 | 在服务关系中明确服务范围、主/备关系、容量和团队 |
| 更换服务官 | 未承接账号/群可直接变更；存在账号/群时发起交接审批 |
| 停用员工 | 禁止再分配新账号或新群；保留历史归属和日志 |
| 归档员工 | 必须无在用账号、无管理群、无未完成交接或审批 |

## 实施优先级

### 第一轮：解决重复与命名

1. 将“客服与服务团队”从主页签改成员工台账的快速筛选。
2. 将“服务官配置”改名为“服务关系”。
3. 用业务项目名称替换技术项目 ID。
4. 将“探哥 / 假面”迁移为历史服务标签，岗位使用标准角色。

### 第二轮：把配置集中到一个入口

1. 新建员工只建立档案。
2. 员工详情加入“服务关系”子页，统一配置项目、地区、主/备服务官和容量。
3. 角色与权限只保留权限模板；员工归属由员工详情配置。

### 第三轮：补齐约束与审批

1. 服务官资格单独启用。
2. 强制校验“项目 + 地区”唯一主服务官。
3. 更换存在资源的服务官走交接审批。
4. 建立服务官负载预警和客服容量预警。

## 审查限制

本次结论基于当前本地原型页面和截图；未验证真实后端权限、审批流、数据同步或移动端表现。技术 ID 与模拟数据问题需要在接入真实项目与员工数据时复核。
