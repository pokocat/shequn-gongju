# 四类运营数据视角重整设计

## 1. 文档目的

将会员、社群、项目、代理四类数据视角从静态排行调整为“业务对象 + 关键经营数据 + 当前运营阶段 + 下一步动作”的运营分析工作台。

本次设计重点解决：

- 会员平台身份、会员等级、平台账号添加状态的快速判断；
- 会员在各项目中的身份等级、项目账号任务、授权和消费关系的展开查看；
- 项目社群服务人员账号与会员资料侧账号身份的匹配；
- 社群围绕触达、互动、项目绑定、课程报名、消费和成交额的运营分析；
- 项目围绕各级别代理、会员发展、订单和交易额的经营分析；
- 代理围绕代理发展、下线会员、订单、交易额、佣金和能力成长的运营分析。

本设计不恢复已废弃的“经营摘要”“会员分层”“RFM”模块。

## 2. 设计范围与边界

### 2.1 首批平台与项目范围

首批固定落地主理人公社及其项目。平台名称固定为：

```text
主理人公社
```

项目名称以当前项目选择器和用户提供的截图为准，统一使用以下名称：

```text
V001 军师
AI超级广告公司
AI艺人孵化
AI数字资产平台
AI大健康
AI知识付费
AI教育
AI明星艺人授权
AI企业礼品采购
```

上述名称必须在项目选择器、项目身份、项目社群、服务人员账号、账号任务、授权关系、订单消费和统计分析中保持一致。不得继续同时使用“AI超级广告平台”“AI艺人孵化平台”等旧名称作为同一项目的替代名称。

### 2.2 必须保留的现有功能

以下功能属于现有账号体系的核心能力，本次只补充业务关联，不调整原有按钮设计和交互入口：

- 添加账号按钮；
- 账号状态判断；
- 登录和绑定状态判断；
- 授权状态判断；
- 添加、绑定、授权的操作日志；
- 失败原因记录；
- 重新添加、重新绑定、重新授权；
- 未添加或未授权时进入引导交互。

### 2.3 页面职责边界

会员主表负责快速判断：

- 会员是谁；
- 平台业务身份和会员等级；
- 平台相关账号是否已添加；
- 有哪些项目身份等级；
- 当前会员运营阶段；
- 下一步应该做什么。

会员个人资料负责展开查看：

- 各项目身份等级和授权关系；
- 各项目对应账号任务；
- 项目服务人员账号；
- 项目账号的登录、绑定和授权状态；
- 项目消费与订单明细；
- 操作日志；
- 激活、转化、复购和升级记录。

## 3. 总体信息架构

四类视角统一使用以下业务结构，但每类视角拥有自己的字段和运营阶段：

```text
业务对象
→ 关键经营数据
→ 运营阶段
→ 问题或机会
→ 阶段化运营动作
```

页面结构保持当前工作台的整体布局：

1. 顶部：平台、项目、范围和时间条件；
2. 左侧：当前视角的运营阶段和任务分类；
3. 中间：业务对象表格；
4. 右侧：当前选中对象的业务档案；
5. 操作区域：根据对象和运营阶段提供可执行动作。

四类视角不强行使用同一套表格字段。统一的是布局和交互习惯，不是业务指标。

## 4. 会员数据视角

### 4.1 核心目标

围绕单个会员快速判断：

- 会员在平台是什么身份；
- 会员等级是什么；
- 平台账号是否已经添加；
- 会员在各项目中是什么身份等级；
- 会员当前处于留存、激活、转化、复购还是升级阶段；
- 下一步应执行什么运营动作。

### 4.2 会员主表字段

主表建议展示：

```text
序号
会员
平台身份
会员等级
平台账号
项目身份
所属社群
入群状态
最近活跃
累计消费
运营阶段
操作
```

#### 平台账号

主表只展示平台相关账号是否已经添加：

```text
已添加
未添加
添加中
添加失败
已解绑
```

未添加、添加失败或需要重新操作时，继续显示现有添加类按钮。主表不展开项目账号的详细绑定和授权日志。

#### 项目身份

项目授权关系直接通过项目身份等级表达：

```text
V001 军师 · PRO会员
AI教育 · 体验官
AI大健康 · VIP
```

判断规则：

```text
存在项目身份等级 = 已建立项目授权关系
不存在项目身份等级 = 尚未授权
```

主表可以先显示摘要，例如“3 个项目身份”，点击后展开具体项目和等级。如果没有任何项目身份，显示“未授权项目”和“发起引导”。

#### 累计消费

主表保留累计消费，用于快速判断会员价值，但不在主表展开每个项目的消费金额。项目维度消费下沉至个人资料的项目与消费区域。

### 4.3 会员运营阶段

会员任务分类建议为：

```text
全部会员
待建立关系
待入群
待激活
已授权未消费
待首次转化
待复购
待升级
高价值会员
沉默会员
流失风险
```

账号或授权状态与运营阶段分开表达。例如：

- 有项目身份等级、项目账号已绑定、消费为 0：已授权未消费；
- 有项目身份等级、账号已绑定、长期没有消费：待复购或流失风险；
- 没有项目身份等级：未授权，需要进入授权引导；
- 有项目身份等级但没有项目账号：已授权但待绑定账号。

### 4.5 项目账号、服务人员与账号任务关联

项目相关账号继续使用现有账号任务体系，不另建一套账号任务模型。

建立项目社群时配置的服务人员账号，是会员资料侧显示项目服务人员和账号身份的依据。配置了什么，会员资料侧就展示什么。

匹配优先级：

```text

→ 当前城市对应服务账号
→ 主理人公社平台级服务账号
→ 未匹配
```

匹配条件包括：

```text

项目
城市
服务人员
账号范围
启用状态
```

第一阶段至少展示主理人公社相关配置，包括平台级账号和项目级账号。后续需要从姓名字符串关联逐步收敛到稳定账号 ID 关联，避免同名或人员变更造成错配。

账号任务在个人资料侧展示：

```text

所属项目
账号身份
负责人员

绑定状态
授权状态

下一步动作
```

## 8. 数据与状态规则

### 8.1 状态层次

账号、授权、消费和运营阶段必须分开建模：

```text
平台账号状态：是否已添加平台账号
项目身份等级：是否建立项目授权关系
项目账号状态：是否登录、绑定和可用
消费状态：是否产生订单和消费
运营阶段：当前应执行的运营动作
```

不能用“已消费”代替“已授权”，也不能用“已授权”代替“账号已绑定”。

### 8.2 项目名称统一

项目名称应由统一配置提供，至少避免以下来源继续分别维护不同名称：

- 主应用项目选择器；
- 生态管理页面项目列表；
- 项目社群规则；
- 会员项目身份；
- 项目账号任务。

如果短期内无法一次性合并数据源，必须增加明确的项目 ID 和标准名称映射，展示层统一使用标准名称。

### 8.3 服务人员账号匹配

服务人员账号应优先以账号 ID 关联，姓名只作为展示字段。项目社群配置和会员资料展示必须使用同一份项目、城市、账号和服务人员关系。

## 10. 实施顺序

### 第一阶段：基础配置统一

- 固定主理人公社项目标准名称；
- 建立项目 ID、标准名称和旧名称映射；
- 对齐项目社群规则和服务人员账号；
- 明确平台级账号、项目级账号和服务人员身份。

### 第二阶段：会员视角

- 主表增加平台账号状态和项目身份摘要；
- 保留现有账号添加、状态判断、日志和引导交互；
- 在个人资料侧增加项目与账号区域；
- 接入项目身份等级、项目账号任务、服务人员和消费明细；
- 增加会员运营阶段和阶段化操作。

### 第三阶段：社群视角

- 增加入群、发言、到达、点击、绑定、报名、消费和成交额字段；
- 增加活动按社群拆分分析；
- 增加社群运营阶段和阶段化动作。

### 第四阶段：项目与代理视角

- 增加项目代理等级、会员发展、订单和交易额分析；
- 增加代理下线会员授权、账号、消费和成交贡献；
- 增加项目和代理运营任务。
