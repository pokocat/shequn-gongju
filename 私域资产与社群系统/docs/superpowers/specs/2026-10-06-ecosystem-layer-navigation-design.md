# 生态平台管理：平铺层级导航与紧凑工作台设计

## 目标

将行业生态 / 平台管理页从“大型层级说明卡 + 多组重复导航”的结构，收敛为以层级选择为起点的紧凑运营工作台。运营者可直接选择超级生态、生态、SaaS 合作伙伴或平台，并在同一屏内理解当前对象、关键经营数据和下一步入口。

## 采用方案

采用方案 A：横向层级条 + 单一工作台。

- 顶部保留页面标题、当前上下文和主要新建操作。
- 使用一条平铺的四层导航替代分散的“第 N 层”说明卡：超级生态、生态、SaaS 合作伙伴、平台。
- 每个层级项显示编号、名称和该层对象数量；当前层使用深色背景与强调色高亮。
- 宽屏展示四项完整层级条；窄屏保持同一顺序，支持横向滚动，不切换为另一套语义。
- 当前对象行紧接层级导航，展示运行状态、对象名称、所属生态与合作伙伴，以及“查看架构”入口。
- 将平台 KPI 收敛为四项紧凑指标：运营项目、平台用户、平台群组、本月营收。
- 仅保留一组工作台导航：平台总览、项目运营、平台级社群、平台配置。原有重复的上层操作按钮应并入这组导航或作为上下文操作，不再单独占据首屏。
- 默认工作台内容显示项目运营摘要和项目列表；已有项目配置、平台级社群和创建流程继续沿用。

## 交互与数据边界

- 层级导航只改变生态管理页当前查看层级，不改变全局 `workspaceContext` 的平台 / 项目隔离规则。
- 选择“平台”层后，平台工作台仍以当前平台为上下文，并继续支持平台切换与项目进入。
- SaaS 合作伙伴仍表示可发展多个平台的合作方身份，不作为系统名称。
- 平台级社群继续使用 `scope="platform"`；项目配置中的社群继续使用 `scope="project"` 和项目名。此次布局调整不得改变数据 scope 或社群规则归属。
- 项目运营入口继续滚动至平台项目区域；平台配置继续打开现有平台配置抽屉。

## 组件边界

在 `EcosystemManagement.tsx` 内把页面结构组织为三个职责明确的展示单元：

1. 层级导航：负责渲染四层及当前层高亮，接收并触发层级选择。
2. 当前对象摘要：负责呈现当前对象路径、状态、关联关系和 KPI。
3. 平台工作台：负责总览、项目运营、平台级社群与配置入口，复用既有列表、滚动定位和抽屉逻辑。

为控制风险，优先抽取局部 React 组件或局部配置常量；不迁移现有生态、平台、项目及社群数据模型。

## 响应式要求

- `lg` 以上：四层导航、对象摘要、四项 KPI 和工作台导航在首屏紧凑排列。
- 小于 `lg`：层级导航可横向滚动；KPI 保持两列或更紧凑的网格；项目列表继续使用已有移动卡片视图。
- 不能依赖 hover 才能理解当前层或进入关键操作。
- 不应出现与全局顶部栏、抽屉导航重叠或遮挡的交互控件。

## 验收标准

1. 用户可在同一处直接点击四个层级，当前层有明确视觉反馈。
2. 平台层首页不再以大型“第 4 层”说明卡作为主要入口，首屏高度显著收敛。
3. 当前平台、归属路径、四项 KPI 和工作台入口在桌面首屏可读。
4. 项目运营、平台级社群、平台配置、查看架构、创建平台的原有入口均仍可访问。
5. 平台 / 项目上下文和社群 Scope 隔离保持不变。
6. 在桌面与移动宽度下，页面无水平溢出、内容遮挡或失效的滚动定位。
7. 通过项目现有构建、测试和 diff 格式检查。

## 非目标

- 不改动生态、SaaS 合作伙伴、平台或项目的底层数据模型。
- 不新增新的结算、权限、社群迁移或归档流程。
- 不重构账号资产中心及其他模块。
