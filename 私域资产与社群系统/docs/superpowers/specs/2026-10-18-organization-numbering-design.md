# 组织层级统一编号体系设计

## 1. 目标

为超级生态、行业生态、SaaS 合作伙伴、平台和项目建立统一、稳定、可追溯的展示编号。编号由系统自动生成，现有静态数据按当前数据顺序补发新编号，用户不在创建表单中手动填写。

## 2. 编号规则

| 层级 | 前缀 | 示例 | 序列范围 |
| --- | --- | --- | --- |
| 超级生态 | `SE` | `SE-0001` | 超级生态独立递增 |
| 行业生态 | `ECO` | `ECO-0001` | 行业生态独立递增 |
| SaaS 合作伙伴 | `SAS` | `SAS-0001` | SaaS 独立递增 |
| 平台 | `PLT` | `PLT-0001` | 平台独立递增 |
| 项目 | `PRJ` | `PRJ-0001` | 项目独立递增 |

序号固定为四位数字，达到 `9999` 后再扩展位数。编号不包含父级编号，父子关系由现有的生态、SaaS、平台和项目关联字段维护。

## 3. 生成与生命周期

- 新建记录时由系统按照对应层级的下一个序号自动生成。
- 各层级分别维护序列，不共享计数器。
- 编号一旦生成即永久保留，不因名称修改、父级调整或状态变化而改变。
- 删除记录后不回收、不复用编号。
- 现有数据按当前数组顺序补发编号：超级生态先生成 `SE-0001`，生态生成 `ECO-0001` 至 `ECO-0005`，SaaS、平台和项目依次补发对应编号。
- 现有项目名称中的业务前缀（例如 `V001`）保留为名称文本，不作为组织层级编号使用；项目另行展示 `PRJ-xxxx`。

## 4. 数据模型

在当前层级记录上增加稳定的展示编号字段：

```ts
{ id: number; code: string; ... }
```

字段约定：

- `id`：继续作为现有前端状态、列表和关联逻辑使用的内部 ID。
- `code`：组织层级展示编号，用于列表、详情、关系树、审批和管理沟通。
- `code` 不参与名称匹配，不替代现有 `id`，不改变现有父子过滤逻辑。

对于当前静态数据，编号直接写入数据定义；新建生态、SaaS、平台和项目时，从现有同类记录中计算下一个未使用序号并生成编号。

## 5. 页面展示

### 关系树

节点名称下方或右侧显示紧凑编号：

```text
健康医药美业生态   ECO-0001
聚域 SaaS          SAS-0001
聚域平台           PLT-0001
AI大健康           PRJ-0005
```

### 详情页

标题区域显示名称和编号；编号使用等宽字体和低对比度辅助色，不抢夺节点名称的主要视觉层级。

### 创建表单

创建表单不增加编号输入框。创建成功后，在成功提示、详情页和关系树中显示自动生成的编号。

## 6. 兼容与验证

- 保持现有内部 `id`、名称、生态 / SaaS / 平台过滤和权限作用域逻辑不变。
- 验证每个层级编号唯一、格式正确、补发顺序稳定。
- 验证创建新记录不会生成重复编号。
- 验证名称修改不会改变编号。
- 验证项目名称中的旧业务前缀与新 `PRJ` 编号可以同时展示且不产生歧义。
- 运行现有测试和 `npm run build`。
