融合模块 · 业务逻辑全梳理

围绕你提出的「账号生命周期」和「三个查看维度」，先把 做什么（What） 和 怎么流转（Flow） 讲清楚，再反推页面结构。

① 核心业务流程：一个工具/账号的一生（生命周期 5 阶段）

下面用"个人微信号"举例，企微/手机/媒体号使用同一套阶段，阶段名完全一致（仅"养号期"内的具体动作不同）。

STAGE · 01
📥 注册入库
采购一批手机卡/微信号/企微席位，批量或单条导入系统。
此时：
• 类型=wechat
• 标识符=wx_0001
• 状态=未启用
• 归属人=空
• 项目=空
• 仅录入"号码/卡号/账号ID"等最少字段
💡 尚未进入可使用池
→
STAGE · 02
🌱 养号期
微信号：每天挂设备、加少量好友、读公众号
企微：每日登录活跃、完善员工资料
媒体号：发几条日常内容养权重
此时：
• 状态=养号中(新增枚举)
• 归属人=空 或 养号专员
• 项目=空
• 运营台账开始记录
  (登录设备/好友数增长/认证)
📊 养号≥7天 且 风控=正常 → 方可进入下一阶段
→
STAGE · 03
🏢 分配到项目
根据新项目的人员编制计划，从可用号池里抽号分配给某项目。
此时：
• 状态=空闲(可领)
• 项目=北京PRO会员
• 归属人=空
• 工具池显示:"可用 · 北京PRO · N个"
🏷 一次可以抽 1 个或批量 N 个
→
STAGE · 04
👤 发放到人
把项目里的空闲号绑定给具体的 SystemAccount（人），此人从此可登录、可加粉、可运营。
此时：
• 状态=使用中
• 项目=北京PRO会员
• 归属人=吴思远(acc-0001)
• 人.assignedTools 增加 1 条
🔐 离职/调岗 → 走 工具交接审批 → 回到阶段3或2
→
STAGE · END
🗄 归档/停用
号被封禁、手机卡注销、媒体号废弃 → 软删除，日志永存。
此时：
• 状态=已停用 / 已归档
• 项目=保留历史
• 归属人=保留历史（用于审计）
• 从所有可用池筛选中默认排除
✅ 这就是为什么"三个模块合并"的根本理由： 上面这个生命周期，从注册到归档是一条连续事件链。原先拆开的三个页面只是这条链上的不同切面（人的切面/工具的切面/微信的切面），本质上应该是同一个模块的不同查看维度。

② 三个查看维度（你提的，完整对应以下三套列表首屏）

无论从哪个维度进入，点击最终都能定位到同一"工具详情"实体，且操作入口完全一致（交接/停用/改项目/改归属人）。

维度 ① · 查看按钮 / Tab
🎯 按账号类型
筛选器（不分页时等于Tab）：全部 / 企业微信 / 个人微信 / 手机号 / 媒体号
首行显示列:
类型 · 标识符 · 昵称/名称 · 当前所属阶段 · 项目 · 归属人 · 风控 · 操作
适用场景：
"我想看全部微信号的养号进度"
"我想看哪些企微席位还是空的"
💡 选中"个人微信"后，"养号进度/好友数"等微信专属列自动展开，其他类型自动隐藏专属列
维度 ② · 查看按钮 / Tab
🏬 按项目
顶部先选项目（可多选），再看这个项目下的账号编排
显示层级（按项目分组）:
┌ 北京PRO会员服务（可用号 8 / 使用中 35 / 养号中 2 / 异常 1）
│  ├ 吴思远 名下工具 4 个
│  ├ 林小燕 名下工具 2 个
│  └ 空闲号池 23 个（未分配到人）
└ 成都分站...
适用场景："北京PRO还差5个号，从号池批拨过去"
"这个项目里的异常号我要一次性看到"
💡 空闲号池的批量分配是本维度的特色按钮
维度 ③ · 查看按钮 / Tab
👥 按人
首列是 SystemAccount 人，点击行展开他名下的全部工具+身份+权限
显示列:
人 · 身份标签(COO/运营/客服) · 所属项目 · 名下工具数 · 异常工具数 · 入职/最近操作
展开 吴思远 → 企微1 / 微信1 / 手机1 / 媒体1 四行（同方案A三级嵌套）
适用场景："新员工入职 → 分配一批号"
"这个人离职 → 他手上所有工具批量走交接审批"
💡 原"账号资产中心"的所有功能（邀请/停用/操作日志/身份权限）= 本维度的 Tab ②

③ 合并后：实体 & 字段如何去重（消除之前的"三份状态"）

合并前三个模块各有一套 status/归属人，现在统一为：以 CommunicationTool（改名 ResourceTool）实体为状态唯一真源，SystemAccount 只保留引用 ID 列表。

🏢 实体A · 人 SystemAccount
—— 不变，只是 status/归属 字段被剥离
✅ 保留：
uid / name / email / phone / status(活跃/停用)
identities[]（身份 + 作用域 + 权限摘要）
createdAt / operationLogs[] / 邀请审核信息
❌ 之前重复的字段 → 删除：
wecomBindings[]（带详情的那种）
wxIds[]（带详情的那种）
字段里的"已绑定/未绑定"等衍生状态
➕ 替换为：
toolIds: string[] —— 只存工具/资源的ID数组
（工具/项目状态通过ID实时join推导，绝不另存）
📱 实体B · 工具 ResourceTool
—— 原 CommunicationTool + 微信台账中"非重复字段"的合并体
✅ 通用字段（4类型都有）：
id / type（wecom/wechat/phone/media）
identifier / name / nickname
★ status（唯一真源）: 未启用 / 养号中 / 空闲 / 使用中 / 待交接 / 异常 / 已停用 / 已归档
riskLevel（正常/关注/高危） · riskDetail（JSON）
boundAccountId（=归属人 SystemAccount.uid，可空）
projectId（=分配到哪个项目，可空）
lastCheckAt · lastLoginAt · createdAt · updatedAt
✅ type=wechat 专属字段（类型驱动展示）：
微信号详情：昵称/认证/QQ号/绑定邮箱/密码密保/紧急联系人/好友数/已删除人数/群数/加粉趋势/微信号二维码
✅ type=wecom 专属：
企业名称/部门/会话存档是否开启/分公司
✅ type=phone 专属：
运营商/实名信息/实名日期/套餐/通话限制
✅ type=media 专属：
平台名（抖音/小红书）/粉丝数/内容量级/创作者中心
⚠️ 一个非常重要的衍生规则： 以后再也不会出现"wx_gz_01 在通讯工具中心显示异常、但在微信账号管理里显示使用中、但在人员列表里又没标红"这种三个地方不一致的情况——因为三个视图都是 JOIN 到同一张 ResourceTool 表读同一个 status 字段。
